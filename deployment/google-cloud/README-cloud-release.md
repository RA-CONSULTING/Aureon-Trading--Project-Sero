# Held cloud source update

This overlay is installation tooling, not evidence that the VM was updated. Do not upload `hold-before/`, test caches or local review receipts as application source.

## Files and roles

- `deployment/google-cloud/build_release_bundle.py`: exports only a reviewed list of exact source paths/hashes to a new bundle.
- `deployment/google-cloud/release_update.py`: prepare, apply, check and rollback a dated source/unit transaction.
- `deployment/google-cloud/operator_runtime_closure.py`: derives and hashes the complete tracked VM operator package closure from the selected commit tree; unknown package assets and partial operator payloads fail closed.
- `deployment/google-cloud/cloud_read_organ.py`: supervises one selected registry-owned process per systemd cgroup; verifies actual capability-gate HOLD behavior, reapplies the six action holds, and gives only the selected provider-reading children an in-memory pinned owner-provider bundle.
- `deployment/google-cloud/cloud_trade_receipt_collector.py` plus `cloud_order_intent_bridge.py`: one supervised service collects signed terminal receipts and, only under a current controller-signed live release, publishes one canonical owner intent from fresh Unified Market Trader evidence while the local trader publisher and executor remain held. Every two minutes it also publishes a zero-order provider-readiness probe. After activation the probe is bound to the exact controller generation and original lease; executor and receipt KMS keys sign detached, balance-free readiness evidence that expires within five minutes and cannot extend release authority. Release preparation refuses a collector update unless both reviewed sources and all imported trading-contract modules are present in the manifest.
- Tests use temporary directories and fake service peers. They do not start cloud services, prompts, learning or trading.

The other agent supplies `cloud_http_runtime.py`, `cloud_operator.py` and `cloud_ui_gateway.py`. Include all three and this overlay's three Python files in the reviewed release payload. Include the verified production frontend dist. Source updates to the five restored cloud boundary files belong in the same release.

## Transaction and recovery

`/srv/aureon/runtime/workspace` stays in place. Manifest-listed source files and the explicitly selected unit files are replaced. For an operator release, old package `.py` files absent from the commit-bound closure are removed as individually backed-up transaction entries, and derived Python bytecode is purged after service stop. State, private files, approvals, provider credentials and logs stay outside the source payload. Existing source/unit bytes are backed up privately inside `/srv/aureon/releases/<dated-id>/backup`; rollback never restores runtime data or old approval snapshots.

The bundle manifest uses schema `aureon.source-release.v1`, an exact 40-character lowercase Git commit revision, its Git tree, a dated release ID such as `20260911T230000Z-0123456789ab`, and a nonempty `files` list of `{path, sha256, size}`. Relative paths map from `files/` to the unchanged workspace root. An operator payload also carries `aureon.operator-runtime-closure.v1`, binding its sorted exact source paths and payload digests to that tree. Bundle creation rejects non-source roots, traversal, symlinks, runtime/private paths, duplicate/case-colliding paths, oversized files and changed reviewed hashes. Source-only publication review remains necessary; the path checks cannot classify every possible sensitive source literal.

Prepare copies and verifies the selected source, compiles Python without importing it, validates the complete operator closure and stale-source inventory, then snapshots exact service ownership/liveness and creates the rollback journal before stopping anything. There is one update lock. `bootstrap` installs the hash-bound token broker source/unit while all workloads retain their prior state; it does not start a publisher. After the external attached-service-account and IAM prepare read-back, apply starts and health-checks the broker first, disables/stops dependent workloads, purges derived bytecode, applies journaled stale-source removals, and atomically replaces each file. Installed source is `root:root` with no write bits; every source ancestor is `root:root` without group/other write access, and both file and directory metadata roll back. It then reloads systemd and starts provider readers, the receipt collector, operator, UI, and the public bridge in that fixed order. The public bridge starts only after its VM-only certificate/key metadata, certificate fingerprint, source revision, and operator/UI health have passed. A controlled restart repeats that order and produces a redacted `aureon.gcp.vm-release-readback.v1` receipt. The commit marker is written last. The selected services must be standalone instances as in the reviewed cloud profile; externally triggered activation units or unselected dependents require separate exclusion before applying.

This is a transaction **to the stopped service set**, with atomic individual file replacements. It is not an instantaneous whole-workspace directory swap. Every existing service that could use the changed shared source must be in the explicitly reviewed affected-service inventory. No full-fleet discovery or shutdown is inferred automatically. The retained old `cloud_organ.py` and unselected service units are not rewritten by this tool.

Failure triggers source/unit rollback and restores original service active/enabled states. New unit links are disabled before their unit files are removed. If the attached VM identity changed outside the updater, rollback restores the files but keeps every managed workload stopped in `rollback_external_identity_required` until a hash-bound provider/IAM rollback receipt proves the original identity and permissions are restored. Unknown ownership, corrupted backups, changed/newer source, an unsuccessful stop or conflicting service inventory blocks rather than overwriting or killing an unrelated process. If the host is interrupted mid-update, `apply` refuses to resume a partial mixed source tree; use explicit `rollback` after inspecting its journal. A `rollback_blocked` phase needs operator review. The tool never deletes whole directories or backups.

`check` verifies current source/unit hashes against the journal's committed or rolled-back phase. It does not attest fresh provider streams. Service liveness and HTTP readiness are also not proof of trading or all-source readiness; root must finish provider/source-clock read-backs before retiring the desktop owner.

## Service ownership and holds

Known cloud HTTP units are `aureon-cloud-operator.service` and `aureon-cloud-ui.service`, using the distinct HTTP shims and Unix identities `aureon-operator` and `aureon-ui`. They use runtime Secret Manager identifiers only; no secret value is supplied in arguments or generated unit files. The operator additionally requires a pinned tenant-auth secret, the pinned exact-shape owner-provider bundle, and an atomic canonical Supabase owner UUID/lowercase confirmed-email commitment pair. The plaintext owner email is never a release input. The UI never receives the owner-provider bundle. Both services remain on loopback and report `/__aureon_health` with the exact revision and `release_authority: false`.

All generated workloads deny the IPv4 and IPv6 metadata endpoints, hide unrelated processes with `ProtectProc=invisible`/`ProcSubset=pid`, mount source read-only, and write only their systemd-owned private state/cache paths plus the two exact operator/trade exchange directories. Google-bound workloads receive a fixed broker token path under `/run/aureon-cloud-identity`; only the root-owned `aureon-cloud-token-broker.service` may reach metadata. The attached broker identity and the exact per-resource workload IAM contract must be provider-read back before deployment. See `OPERATOR_RUNTIME_CLOSURE.md` and `trading-control/resource_contract.json`.

For data/runtime services use explicit `aureon-organ@<name>.service` selections from `READ_ORGANS`. These include current analysis-only `unified_market_trader`, `unified_market_status`, `market_stream_feeder`, HNC/Queen, assessment and passive data producers. Only `heartbeat_daemon` and `hnc_live_daemon` are in `PROVIDER_CONFIG_ORGANS`: their runner fetches the same pinned owner-provider bundle in an isolated worker, disables dotenv loading, and adds the validated six fields only to that selected child launch environment. Other organs have those six names stripped from their child specification. The existing `sero_autonomous_expansion` service can only be retained by the installer when it is already active. `unity_supervisor`, `operator_gateway`, `frontend_vite`, radar execution, action hubs and arbitrary services are not eligible. No second registry HTTP owner is started.

The runner validates real `deployment_hold` verdicts for trading, process execution, code execution, outbound communication and non-public network actions; an environment flag by itself fails this check. It never adopts an already-running process. It checks the new PID's cgroup and creation time, and only stops a still-matching registry owner while holding the registry's existing lock.

Every generated unit and selected registry child carries:

```text
AUREON_DEPLOYMENT_HOLD=1
AUREON_DISABLE_REAL_ORDERS=1
AUREON_DISABLE_EXCHANGE_MUTATIONS=1
AUREON_ORDER_INTENT_PUBLISH=0
AUREON_LIVE_TRADING=0
AUREON_UNIFIED_ORDER_EXECUTOR=0
```

## Installation plan — do not execute before VM discovery/review

1. Root reads the actual VM service/PID inventory, confirms the rollback snapshot, dependency availability and free space, then finalizes the affected owned-service list. Commission the broker and four fixed workload identities exactly as recorded in `trading-control/resource_contract.json`; the attached broker identity must have no data-plane roles, and the retired shared runtime identity must retain none. Create only the documented private state/cache and writer-owned operator/trade exchange paths.
2. Root freezes the isolated source checkout and verified dist at the intended pushed revision. Run `generate_reviewed_paths.py --source <absolute-frozen-checkout> --source-revision <full-sha> --output <new-reviewed-paths.json>`. It derives the complete operator, collector, UI, organ, broker and public-bridge closure, includes the complete generated frontend dist, hashes tracked inputs from their exact Git commit blobs so `core.autocrlf` cannot change the receipt, and writes only `{path, sha256}` rows. Do not select live runtime data or a dirty directory recursively.
3. Run `public_bridge_certificate_receipt.py` on the VM to produce a fresh, redacted `aureon.gcp.vm-public-bridge-certificate-receipt.v1` for the existing public certificate. The script parses the X.509 certificate, requires it to be currently valid with at least 86,400 seconds remaining, requires the exact single IP SAN `10.40.0.2`, and hashes its DER bytes without opening the private key. Run `build_release_bundle.py --source <frozen-checkout> --paths <reviewed-paths.json> --destination <new-bundle-dir> --revision <full-sha> --release-id <UTC-dated-id> --frontend-build-env <public-build-env.json> --bridge-certificate-receipt <receipt.json> --bridge-certificate-receipt-sha256 <exact-file-sha256>`. The builder exports the exact Git tree, rebuilds ignored `frontend/dist` from that commit with the lockfile, and requires byte-for-byte equality. The manifest stores only public environment keys and their aggregate hash. Run the finite publication secret scans against this exact bundle and its manifest.
4. Transfer the verified bundle and trusted updater through the existing authenticated cloud channel. Recheck all hashes on the VM. Run the current release's `deployment/google-cloud/test_deployment_hold.py` in its isolated temporary workspace before installation. It must prove restored release flags, matrix approvals and door approvals do not release actions or replay signals.
5. As the VM administrator, run `release_update.py prepare --bundle <verified-bundle> --service <owned-unit> ... --project <verified-project> --secret <operator-http-secret-id> --secret-version <numeric-version> --tenant-secret <supabase-tenant-secret-id> --tenant-secret-version <numeric-version> --provider-secret <owner-provider-secret-id> --provider-secret-version <numeric-version> --owner-subject <canonical-supabase-uuid> --owner-email-sha256 <lowercase-confirmed-email-commitment>`. Defaults are the existing workspace, `/srv/aureon/releases`, and `/etc/systemd/system`. Inspect the resulting journal, source-directory metadata plan and exact affected-service list. It contains only pinned identifiers and commitments, never secret values or plaintext owner email. The provider reference is required when the service set includes the private operator, `heartbeat_daemon`, or `hnc_live_daemon`; it is omitted from every other generated command.
6. Run `release_update.py bootstrap --release /srv/aureon/releases/<dated-id>`. Inspect its read-back before changing the VM identity. Run `vm_identity_commission.py plan`, review its provider-bound hash, then use its separately acknowledged `apply` operation to stop the existing VM, attach only the broker service account with the `cloud-platform` scope, restart, and read the identity back. Keep the plan and final receipt at different absolute paths. Before every provider mutation the tool fsyncs `<receipt-stem>.progress.json`; after an uncertain command it reads the provider state and resumes the next required step. A failed identity change makes one idempotent recovery-start attempt and records either `recovered_running` or `recovery_required`, including the redacted provider state, so a stopped VM is never unreported. Re-run the same acknowledged plan to resume. The tool grants no IAM role. Apply the exact workload impersonation/resource IAM contract through authority `resource-prepare`.
7. Deploy all seven Cloud Run revisions through `cloud_run_stage.py` with no traffic, passing the immutable-image build receipt and its exact SHA to both `plan` and `stage`. Its fsynced progress receipt supports provider-read-back recovery after a partial or uncertain deploy. Complete subscription replacement and receipt-gated legacy retirement while both publisher units remain inactive and disabled or masked. Archive evidence must precede the zero-backlog observation window, and the retirement command rechecks the live publisher freeze before and after every exact-name deletion. Retain the post-deletion retirement-phase receipt and its separately acknowledged deletion-time owner receipt. Then create the read-only authority staged-attestation receipt with the same immutable-image receipt/hash. Run `release_update.py apply --release /srv/aureon/releases/<dated-id> --authority-receipt <staged-attestation.json> --authority-receipt-sha256 <exact-file-sha256>`, then `check`. The accepted receipt has `status=staged_attested`, `phase=staged-revision-attestation`, `provider_readback_ok=true`, a hash-bound exact seven-service provider readback, `provider_error_codes=[]`, `cloud_run_staged_without_traffic=true`, and `vm_readback_deferred_to_release_receipt=true`. It carries the immutable-image receipt's exact certificate-receipt hash, DER fingerprint, IP SAN, validity interval and 86,400-second minimum. Preserve `vm-release-receipt.json` and its journaled SHA. Apply never accepts a resource-prepare or finalize receipt.
8. Perform the separately controlled VM reboot. After the VM is running, run `release_update.py reboot-readback --release /srv/aureon/releases/<dated-id>`. This read-only step requires a changed boot-id hash, exact active/enabled successful units, fresh broker tokens for the four fixed workload identities, operator/UI/bridge health, and the same current certificate evidence bound by the immutable-image receipt, then writes `aureon.gcp.vm-reboot-continuity.v1` with no tokens or secrets.
9. Supply the exact immutable-image, VM release, reboot-continuity and post-deletion legacy-retirement receipt hashes to authority finalize, along with the archived-backlog, zero-backlog and deletion-time owner receipts that the retirement receipt binds at deletion time. A later fresh owner receipt remains the finalize-time identity proof; it does not replace the original deletion-time proof. Finalize revalidates the complete certificate chain and removes only any newly observed contract-listed IAM extras, retaining its provider read-back receipt. Root verifies cloud HTTP revision, auth isolation, source clocks, provider state, database integrity, ownership, and continuity before any desktop shutdown. On interruption or failure, inspect and run rollback for that exact release; an external identity change requires the separate provider/IAM rollback receipt before workloads can restart. No live action release follows from installation or health checks alone.

Rollback preserves the original source/unit configuration, source-parent metadata, individually removed stale package source, and original service status, so the pre-update cloud must itself already have the validated deployment hold. If that original state is unheld or unverified, do not apply this update until root establishes a safe baseline. Derived bytecode is deliberately not restored.
